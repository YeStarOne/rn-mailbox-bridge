# ZCode 适配：用定时任务通道唤醒休眠会话

[English](zcode-integration.md)

本仓库的邮箱桥解决的是"完全没有 harness"的成员。反过来还有一类：harness 齐全（ZCode），能力不缺，缺的是**时效**——会话睡着了。本文详细拆解我们生产环境怎么让休眠的 ZCode 会话被主动唤醒、读信回信，全程无需人工敲一个字；以及不开 watcher 时，怎么用纯官方原生工具做到同样的事。

## 1. 问题：回合边界投递 vs 睡着的会话

Reason Network 给会话送信靠 **turn 边界**触发的 hook（会话启动、回合结束、下一次工具调用）。会话在跑时没问题；但一个回合已经结束的聊天会话只会等用户再输入：

* 没有东西触发 hook，
* 没有东西把消息注入上下文，
* 于是信就静静躺着——可能躺好几天。

团队列表里它"在线"，实际是聋的。多 agent 团队最容易死在这：队友发了 ASK，会话没醒，没人 ACK。

## 2. 现成的通道：ZCode 自己的定时任务调度器

ZCode 自带持久化自动化调度器（定时任务背后就是它）：它大约**每 20 秒**重读一次任务索引（`~/.zcode/v2/tasks-index.sqlite`），认领到期的 run；绑定到某个会话的 run 会先 `resumeTask`（唤醒该会话）再 `sendPrompt`（投喂提示词）。`trigger='manual'` 的 run 行见到即认领。实测验证过完整闭环（含结算：绑定会话的回合跑完、run 记 `succeeded`、锁释放）。

这就是缺的那条投递通道。**一次唤醒 = 往 ZCode 自己的任务库里插一条 manual run**——不注入 agent、不抓屏、不用私有 API。

## 3. 我们的 watcher 怎么做（daemon 侧；此处只记行为，代码未公开）

我们的 Reason Network fork 给 daemon 加了一个小 watcher。行为如下：

1. **每个会话一条隐藏的 helper 自动化。** 首次需要时，daemon 往该会话的任务库插一条自动化：id `rnwake:<会话键>`、`enabled=0`、lifecycle `paused`、cron 表达式 2 月 29 日（`0 4 29 2 *`）——**永远不会自己定期触发**，它存在的意义只是承载 manual run。它在自己独立的 id 命名空间里，用户的自有自动化绝不会被碰或被复用。
2. **来信 → 戳一下。** 消息投给一个**空闲**的 ZCode 会话（agent=zcode、不在回合中）时，daemon 给该会话的 helper 插一条 manual run。
3. **约 20 秒内 ZCode 唤醒该会话**（`resumeTask` + `sendPrompt`），按配置的模型线执行。
4. **信本身从不经过自动化。** 唤醒提示词是一句固定话术：*"Reason Network 唤醒：有队友消息等你处理，它们已被注入本回合的上下文——按项目消息规范处理并回复。若上下文里确实看不到任何队友消息，调用 check_inbox 再确认一次；两边都为空就回一句「空唤醒」，不要开始任何其他工作。"* 消息本体由 Reason 自己的 hook 注入被唤醒回合的上下文——本来就属于它的投递通道。
5. 会话处理、回信、继续睡。run 结算，ZCode 的单飞 `running` 标志释放。

生产实测端到端延迟：从"队友点发送"到"收件人正在读信箱"约 **20–30 秒**，哪怕该会话已经几小时没人碰过。

## 4. 安全栏

* **忙碌会话绝不打断。** 回合进行中的会话在下一个工具调用边界正常收信（hook 原生路径），不插唤醒。
* **按会话节流**（默认 120 秒，下限 5 秒）：一阵消息只触发一次唤醒，后续消息搭同一回合的车。
* **单飞。** 已有唤醒在跑（ZCode 的 `running` 标志）时不再排队第二条；消息等下一个回合边界。
* **固定且极简的提示词。** 唤醒词只说"做什么"，从不说"消息里有什么"——任务库里不流经任何敏感内容。
* **总开关**（`REASON_NETWORK_WAKE=0`）一键全关。

## 5. 模型线自愈（最微妙的一条）

helper run 跑在**配置好的可用快速模型线**上，而不是会话上次用的那条——把一个卡在配额耗尽模型上的会话唤醒，只会得到一个空转回合。而且如果**上一次**唤醒 run 记了 `failed`，下一次自动换**备用线**：主线配额没了 → 唤醒自愈切到备线；由于 ZCode 会把 run 配置应用到被恢复的会话上，会话之后的自己的回合也留在可用线上。没有人需要盯着报错界面。

## 6. 边界与怪癖

* **离线会话**：发给"记得但已关闭"会话的消息同样能唤醒它（`resumeTask` 把它带回来）——前提是它在过去 **7 天**内出现过。超过 7 天视为翻篇，保持沉睡（唤醒一个一周没碰的会话既失礼，上下文多半也过期了）。
* **不可注册的会话会被跳过**：键退化成 `proc:<pid>` 的会话（注册早于 harness 上报真实会话 id）无法被调度器寻址；它下次工具调用时会自愈成可唤醒的 `sess_*` 键。
* **只对 `zcode` 会话生效。** cli/邮箱桥会话（见 [README](../README.zh-CN.md)）被刻意排除——它们靠 `listen --as` 轮询，戳它们没有意义。

## 7. DIY：纯原生工具做到同样的事

如果你用的是上游原版 Reason Network（没有 watcher），任何带定时自动化的 harness 都能模仿这套机制——watcher 是"到达即插 manual run"，DIY 版是"按节拍定时触发"：

**变体 A——会话有 Reason Network MCP 工具。** 在该会话*内部*建一条循环自动化（ZCode 里直接让会话自己建，比如每 30 分钟），提示词：

```text
Reason Network 心跳（每 30 分钟）：调用 check_inbox。
- 有未读消息：按团队 playbook 处理并回复（LOCK / PROGRESS / DONE / ASK+ACK）。
  要开长任务先发 LOCK。
- 无未读：本轮立即结束，不要开始其他工作。
- 若最近 10 分钟内用户亲自参与过本会话，跳过本次心跳。
无论哪种情况，本轮都保持简短。
```

**变体 B——会话只有 shell。** 同样思路，用官方 CLI：

```text
Reason Network 心跳（每 30 分钟）：运行 `reason-network listen --as <名字>`。
- 输出以 "No messages" 开头：本轮立即结束。
- 否则消息已被打印出来：处理它们，并用
  `reason-network send <队友地址> --from <名字> -`（正文走 stdin）回复。
- 若最近 10 分钟内用户亲自参与过本会话，跳过本次心跳。
无论哪种情况，本轮都保持简短。
```

**与 watcher 的取舍：**

| | watcher（我们的 fork） | cron 心跳（原生） |
|---|---|---|
| 唤醒延迟 | ~20–30 秒 | 一个间隔（建议 ≥15–30 分钟） |
| 空闲时的 token 成本 | 零 | 每个间隔一次短运行 |
| 用户正在打字时触发 | 绝不（忙碌跳过） | 需要自己在提示词里 instruct 跳过 |
| 配置成本 | 自动 | 每会话一条自动化 |
| 上游原版可用 | — | 可以 |

两条实操建议：心跳回合必须**短且终点明确**（一个会开新项目的心跳会变成团队里最吵的队友）；已经享受 watcher 的会话不要再加心跳。

## 8. watcher 配置项

| 环境变量 | 含义 | 默认 |
|---|---|---|
| `REASON_NETWORK_WAKE` | `0` 彻底关闭唤醒 | 开 |
| `REASON_NETWORK_WAKE_THROTTLE_SECS` | 同会话两次唤醒的最小间隔（≥5） | 120 |
| `REASON_NETWORK_WAKE_PROMPT` | 固定唤醒提示词 | 见 §3 |
| `REASON_NETWORK_WAKE_MODEL` | 唤醒 run 用的模型线（ZCode model_selection JSON；`null`=跟随工作区默认） | 可用快速线 |
| `REASON_NETWORK_WAKE_MODEL_FALLBACK` | 上次唤醒失败后改用的线 | 备用快速线 |

同样的值也可以写在 daemon 的 `config.toml` 里；环境变量（比如由插件的 userConfig 注入它拉起的 MCP server）优先。
